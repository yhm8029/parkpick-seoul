# 추천 결과 패널 전환 설계

## 목표

사용자가 출발지, 목적지, 방문 조건을 입력하고 `추천 주차장 찾기`를 실행했을 때 기존 입력 폼 아래에 결과를 추가하지 않는다. 추천 API가 성공하면 같은 왼쪽 영역의 입력 폼을 추천 카드 1~3개로 교체한다. 오른쪽 지도는 자리를 유지하면서 추천 마커와 선택된 주차장 정보를 갱신한다.

## 현재 문제와 원인

`AppShell`은 입력 플래너를 항상 렌더링하고 `result`가 생기면 별도의 결과 섹션을 페이지 아래에 추가한다. 추천 성공 후 `scrollIntoView`로 하단 섹션까지 이동하기 때문에 입력 화면과 결과 화면이 한 페이지에 동시에 남는다. 모바일에서도 성공 직후 `mobileView`를 `map`으로 설정해 사용자가 기대한 추천 카드가 먼저 나타나지 않는다.

## 선택한 접근

시각 비교안 A를 적용한다.

- `result === null`: 왼쪽에 기존 방문 계획 입력 폼을 렌더링한다.
- `result !== null`: 같은 왼쪽 자리에 결과 헤더와 응답에 포함된 `ParkingCard` 1~3개를 렌더링한다.
- 오른쪽 `MapPanel`, 경로 요약, 선택 상태는 같은 위치에서 유지한다.
- 기존 하단 결과 섹션은 제거한다.
- 별도 화면 단계 상태를 추가하지 않고 `result`를 화면 전환의 단일 기준으로 사용한다.

이 방식은 입력값과 결과 화면 상태가 어긋나는 중복 상태를 피하면서 사용자가 요청한 “입력 영역이 카드 영역으로 바뀌는” 동작을 직접 구현한다.

## 상태와 데이터 흐름

1. 사용자가 출발지, 목적지, 도착 시각, 체류 시간, 추천 기준, 최대 도보 시간을 입력한다.
2. `추천 주차장 찾기`를 누르면 입력 폼을 유지한 채 버튼에 로딩 상태를 표시한다.
3. API 요청이 실패하면 `result`를 설정하지 않고 입력 폼 안에 오류를 표시한다.
4. API 요청이 성공하면 응답을 `result`에 저장하고 1순위 주차장을 `activeId`로 선택한다.
5. `result`가 생긴 렌더에서 왼쪽 입력 폼이 결과 카드 목록으로 교체된다.
6. 결과 화면의 `조건 변경`을 누르면 입력값은 보존하고 `result`와 `activeId`만 초기화해 입력 폼으로 돌아간다.
7. 카드 선택은 `activeId`만 변경하며 지도 마커, 선택 경로, 네비게이션 버튼을 같은 주차장으로 동기화한다.

각 추천 요청은 `AbortController`로 관리한다. 새 요청을 시작하거나 입력값을 변경하거나 `조건 변경`을 누르면 진행 중 요청을 취소한다. 최신 요청의 성공 응답만 `result`와 `activeId`를 갱신해 이전 조건의 늦은 응답이 결과 화면을 덮어쓰지 못하게 한다.

추천 성공 전에는 전환하지 않는다. 목적지 선택만으로 자동 요청하지 않으며, 사용자가 방문 조건을 확정하고 버튼을 눌러 성공 응답을 받은 시점을 전환 경계로 삼는다.

## 화면 구성

### 입력 모드

- 왼쪽: 기존 `control-card` 전체
- 오른쪽: 목적지 미리보기 지도, 출발·도착 요약, 서비스 원칙
- 요청 실패: 입력 폼 하단의 기존 오류 영역

### 결과 모드

- 왼쪽 상단: 목적지명, 데이터 모드 배지, 데이터 안내문, `조건 변경` 버튼
- 왼쪽 본문: 순위별 `ParkingCard` 3개와 예약이 아니라는 면책 안내
- 오른쪽: 기존 `MapPanel`과 출발지→목적지 `.route-summary`를 유지한다. 제거되는 하단 결과의 `.active-route`와 compact `NavigationButtons`는 결과 모드에서 `MapPanel` 바로 아래로 이동한다.
- 결과 모드에서는 서비스 원칙 영역을 숨겨 추천 비교에 집중한다.

기존 입력 폼은 `AppShell`에 유지하고, 기존 하단 결과 마크업은 새 `RecommendationPanel` 컴포넌트로 옮긴다. 이 컴포넌트는 결과 데이터, 활성 주차장 ID, 카드 선택, 조건 변경 콜백만 받는다. 관련 없는 상태 관리나 페이지 구조는 리팩터링하지 않는다.

## 반응형 동작

- 입력 모드의 기존 850px 반응형 기준은 유지한다.
- 결과 모드는 1050px 초과에서 `minmax(520px, 1fr) minmax(420px, 1fr)` 2열로 표시한다.
- 681px~1050px 결과 모드에서는 카드 목록을 먼저, 지도를 다음 순서로 세로 배치한다.
- 680px 이하: 기존 `목록/지도` 토글을 유지하고 추천 성공 직후 기본값을 `list`로 설정한다. 결과 헤더와 `조건 변경` 버튼은 항상 표시한다. `list`에서는 카드 목록만 표시하고 지도측 래퍼(`MapPanel`, `.active-route`, 출발지→목적지 요약)를 숨긴다. `map`에서는 카드 목록을 숨기고 지도측 래퍼를 표시한다.
- 결과에서 조건 변경 후 다시 추천하면 모바일 기본값을 다시 `list`로 초기화한다.

## 오류와 빈 결과

- 네트워크 오류 또는 비정상 응답: 입력 모드를 유지하고 입력값을 보존한다.
- 추천 결과가 0개인 성공 응답: 결과 모드로 전환하지 않고 조건을 조정하라는 오류를 입력 폼에 표시한다.
- 새 요청을 시작할 때 이전 오류를 지운다.
- 결과를 무효화하거나 조건 변경으로 복귀할 때 이전 `activeId`를 제거한다.

## 접근성

- 결과 패널 제목에 `tabIndex={-1}` 기준점을 두고 추천 성공 후 해당 제목으로 포커스를 이동한다.
- 별도의 시각적으로 숨긴 `role="status"` 영역에는 `${destinationName} 추천 ${count}개를 불러왔습니다` 형식의 문장만 알려 중복 낭독을 피한다.
- 카드 선택과 지도 마커 선택은 기존 버튼 의미와 키보드 동작을 유지한다.
- 애니메이션은 기존 `prefers-reduced-motion` 규칙을 존중한다.

## 테스트와 검증

UI 검증을 위해 `@testing-library/react`, `@testing-library/user-event`, `jsdom`을 개발 의존성으로 추가한다. `tests/**/*.test.tsx`를 Vitest 대상에 포함하고 UI 테스트 파일만 jsdom 환경에서 실행하며, 기존 도메인 테스트는 node 환경을 유지한다. 최소 테스트는 다음과 같다.

1. 추천 성공 시 방문 계획 입력 폼이 사라지고 응답에 포함된 추천 카드 1~3개가 같은 영역에 나타난다.
2. `조건 변경`을 누르면 기존 입력값을 보존한 입력 폼으로 돌아가고 이전 추천 카드는 사라진다.
3. 모바일 결과의 기본 보기는 `목록`이며 지도 탭으로 전환할 수 있다.
4. API 실패 또는 빈 추천 결과에서는 입력 폼을 유지하고 오류를 표시한다.
5. 카드 선택 시 활성 카드와 지도 선택 상태가 같은 ID를 사용한다.

구현 후 다음 명령을 모두 실행한다.

```bash
npm run typecheck
npm test
npm run build
```

마지막으로 데스크톱과 모바일 뷰포트에서 실제 추천 흐름, 조건 변경 복귀, 목록·지도 토글, 네이버 지도 로딩을 브라우저에서 확인한다.

## API 키 취급

네이버 Web Dynamic Map에는 로컬 `.env.local`의 `NEXT_PUBLIC_NAVER_MAP_NCP_KEY_ID`만 사용한다. Client Secret은 현재 브라우저 지도 코드에 필요하지 않으며 `NEXT_PUBLIC_*` 변수나 Git 추적 파일에 저장하지 않는다. `.env.local`은 커밋하지 않는다.

## 구현 및 검토 흐름

- 구현 작업은 테스트, 상태 전환, 결과 패널, 반응형 스타일처럼 작은 단위로 나누어 MiniMax M3에 전달한다.
- MiniMax M3 호출은 thinking을 비활성화한다.
- GPT-5.6 Codex 검토 모델은 위험도에 따라 선택한다. 상태 전환·보안·회귀 위험은 Sol, 일반 UI·CSS는 Terra, 경미한 확인은 Luna가 맡는다.
- 사용자가 이번 작업의 중간 커밋과 푸시를 명시적으로 요청했으므로, 통합 가능한 단위마다 검증 후 커밋하고 `origin/main`에 푸시한다.

## 범위 제외

- 목적지 선택 즉시 자동 추천
- URL 기반 다중 페이지 라우팅
- 주차 데이터 또는 추천 점수 알고리즘 변경
- 네이버 Client Secret을 사용하는 서버 API 추가
- 지도 공급자 또는 네비게이션 연결 방식 변경
